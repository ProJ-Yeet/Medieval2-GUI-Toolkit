Lua scripts

Change a Medieval II mod with a few lines of code: every spearman one point braver, every mercenary 20% cheaper, a word replaced in every message, a unit copied for a new faction. This guide starts from nothing and ends with every function a script can call.

What Lua scripts are

A Lua script is a small text file of instructions. The toolkit runs it against one mod, and the script reads the mod (its units, buildings, traits, campaign) and asks for changes. The changes are made by the toolkit's own editors, the same ones behind its screens, so every rule those screens keep (a unit name that must be unique, a tile that must be on the map, a number that must be whole) holds for a script too.

Think of it as a batch edit written as a recipe. Anything you would do by clicking fifty times in the Unit Editor, a script does in one run, the same way every time, and you can send the script to someone else to run on their copy of the mod.

What it is not. These scripts run inside the toolkit, while you are modding. They are not scripts the game runs (that is M2TWEOP's own Lua, a different thing), and nothing here is loaded by Medieval II.

Three promises make it safe to try things:

  • Dry run first. A dry run shows exactly which files would change, line by line, and then puts everything back. Nothing is kept until you press Apply.
  • One run, one Undo. An applied run is a single entry in the toolkit's Log, however many edits it made. Its Undo takes the whole run back.
  • All or nothing. If any edit is refused, or the script stops with an error, every edit it had made is undone. A script never leaves a mod half changed.

Your first script, in the app

The Lua tab is a beta feature, so switch it on first.

  1. Open Settings (top bar) and tick Opt into beta features.
  2. Pick your mod in the Mod box at the top.
  3. Open the menu (☰) and go to Scripts and add-ons, then the Lua tab.
  4. Replace the text in the editor with this: 
    local count = 0
for _, unit in ipairs(toolkit.units()) do
  if unit.category == "cavalry" then
    count = count + 1
  end
end
print("cavalry units:", count)
  5. Press Dry run. Under Printed you see how many cavalry units the mod has. This script only reads, so it says the script changed nothing.

Now a script that changes something. Open the Open a script... list, pick raise_morale.lua under Examples, type faction=england (or a faction your mod has) in the Arguments box, and press Dry run. The report lists the units it would change, and under each file a coloured diff: red lines go, green lines come in. Nothing is written yet. Press Apply to keep it; the Log (top bar) then shows the run under Lua scripts, with an Undo button.

Tip: type toolkit. in the editor and a list of everything you can call opens. Ctrl+Space opens it again. The What a script can call list under the editor has the same names with one line each.

Save keeps your script under the name in the box next to it, in the toolkit's config/lua_scripts folder. Saved scripts appear in the Open a script... list.

Dry run, Apply and Undo

Every run does the same thing: it runs your script from the top, and each edit the script asks for is made at once, so the next line of the script sees it. When the script ends:

  • Dry run compares every touched file with how it was, puts every file back byte for byte (and checks that it did), and shows you the comparison. The Log keeps nothing.
  • Apply keeps the files as the script left them and folds all its edits into one Log entry. The Log's Undo on that entry, or lua_cli.py undo <id>, puts back every file the run touched.

Close the game first. A dry run writes the mod's files while it runs and puts them back at the end. Do not run scripts while Medieval II has the mod open.

The Log is not a backup of your whole mod. It covers the files the toolkit wrote. Keep your own copy of a mod you care about, as with any editor.

If an edit is refused (say you rename a unit to a name another unit has) the run stops there, every edit before it is undone, and the report names the edit and the reason. The same happens when the script itself fails, for example by reading a field of something that is nil.

Lua in fifteen minutes

You do not need to be a programmer. These are the only parts of Lua the examples use.

Comments, values and variables

-- two dashes start a comment: Lua ignores the rest of the line
local faction = "england"    -- text (a "string"), in quotes
local bonus = 2              -- a number
local hidden = true          -- true or false
local nothing = nil         -- nil means "no value"

Write local the first time you name a variable. After that, bonus = bonus + 1 changes it.

Text

local name = "Feudal" .. " Knights"     -- .. joins text: "Feudal Knights"
print(#name)                            -- # is the length: 14
print(name:upper())                     -- FEUDAL KNIGHTS
print(("%s has %d men"):format(name, 40))  -- %s text, %d whole number
print(tonumber("12") + 1)               -- text to number: 13
print(tostring(13))                    -- number to text: "13"

Tables: lists and records

A table holds many values. As a list it is numbered from 1 (not 0); as a record it has named fields.

local factions = { "england", "france", "hre" }
print(factions[1])       -- england
print(#factions)          -- 3, how many

local pool = { unit = "Peasants", maximum = 4 }
print(pool.unit)          -- Peasants
print(pool["maximum"])    -- 4, the same as pool.maximum
local era = { ["era 0"] = "england" }  -- a name with a space goes in [" "]

Decisions and loops

if unit.category == "infantry" and not unit.mercenary then
  print("a regular foot unit")
elseif unit.category == "cavalry" then
  print("horse")
else
  print("something else")
end

-- go through a list: i is the place (1, 2, 3...), u the value
for i, u in ipairs(toolkit.units()) do
  print(i, u.type)
end

-- go through a record's fields
for key, value in pairs(unit.fields) do
  print(key, value)
end

for n = 1, 5 do print(n) end   -- 1 to 5

== compares, ~= means "not equal". _ is the usual name for a value you do not need.

Functions

local function owned_by(unit, faction)
  for _, owner in ipairs(unit.ownership) do
    if owner == faction then return true end
  end
  return false
end

Finding things inside text

Many EDU values are text with commas, like stat_mental = "9, normal, trained". Two ways to take it apart:

-- 1. split on commas into a list
local parts = {}
for piece in unit.fields.stat_mental:gmatch("[^,]+") do
  parts[#parts + 1] = piece:match("^%s*(.-)%s*$")   -- trimmed of spaces
end
print(parts[1])   -- "9"

-- 2. match a shape: (%d+) captures a whole number
local morale = unit.fields.stat_mental:match("^%s*(%d+)")

Lua's patterns are like simple wildcards: %d a digit, %s a space, + one or more, .- as little as possible, ( ) what to keep. In a pattern, . % - + * ? [ ] ^ $ ( ) have special meanings, so put a % before them to mean the character itself.

Stopping, and errors on purpose

local faction = assert(args.faction, "give faction=<name> as an argument")  -- stop with a message if missing
if not toolkit.unit("Peasants") then error("this mod has no Peasants") end
local ok, why = pcall(toolkit.edit_unit, "Peasants", { soldier = "x" })  -- try; carry on if refused

Lua is case sensitive: Toolkit is not toolkit, and a unit called "Peasants" is not "peasants".

How a script talks to the mod

Everything comes from one table, toolkit. Its functions are of two kinds:

  • Reads, like toolkit.units() or toolkit.unit("Peasants"), give you copies of the mod's data as Lua tables. A list function gives a list in the order of the file; a single-item function gives the item, or nil if there is no such thing.
  • Edits, like toolkit.edit_unit(...), change the mod. They return nothing. A refused edit stops the script with the reason (unless you call it inside pcall).

What you read is a copy

The tables a read gives you are read-only: unit.category = "cavalry" stops the script with this table is the mod as read; change it through toolkit.edit_* functions. To change something, call its edit function. To work with a list you want to change, copy it first:

local pri = {}
for i, v in ipairs(unit.stat_pri) do pri[i] = v end
pri[1] = tostring(tonumber(pri[1]) + 1)
toolkit.edit_unit(unit.type, { stat_pri = pri })

A read after an edit sees it

Edits happen as the script makes them, so you can build on them: copy a unit, then edit the copy; rename a modeldb entry, then point another unit at the new name. Read things again after an edit rather than keeping an old copy, especially where line numbers are involved (buildings, recruit pools).

Values you pass

  • Text fields take text or a number: { soldier = "peasants, 40, 0, 1" }, { population = 2500 }.
  • In edit_unit, a list is written joined with ", ": { ownership = { "england", "scotland" } } becomes ownership england, scotland. Other functions that take a list (a trait's characters, a level's effects) keep it a list.
  • false means "off" or "take it out", in the way each function says: in edit_unit it removes the line ({ armour_ug_models = false }), in edit_strings it removes the entry, in clone_faction art = false copies no pictures. The reference says it for each function.
  • Places in lists count from 1, as everywhere in Lua.

Patterns you will use

Only some units

for _, u in ipairs(toolkit.units()) do
  if u.category == "infantry" and u.class == "spearmen" and not u.eop then
    -- ...
  end
end

Check before you change

if toolkit.unit(args.name) then
  error(args.name .. " is already a unit")
end

Skip what the editors refuse, and say so

for _, u in ipairs(toolkit.units()) do
  local ok, why = pcall(toolkit.edit_unit, u.type, { mount = "heavy horse" })
  if not ok then print("skipped " .. u.type .. ": " .. why) end
end

A refused edit inside pcall has changed nothing; the run goes on.

One script, many uses

local faction = args.faction or "england"        -- a default
local by = tonumber(args.by or "1")              -- args are always text

Share code between scripts

Put functions in a file next to your scripts, say util.lua, ending in return { owned_by = owned_by }, and load it with local util = require "util". require only reads from the script's own folder (and folders under it: require "lib.util" is lib/util.lua).

Reference

Every function, with what it takes and gives. read functions only read; edit functions change the mod. In the signatures, ? after a name means you may leave it out.

Units (export_descr_unit.txt)

toolkit.units() → Unit[]read

Every unit in the mod in file order: the EDU first, then any M2TWEOP unit files.

toolkit.unit(type) → Unit or nilread

One unit by its type line, exactly as written there.

A Unit has these fields:

FieldWhat it is
type, dictionaryIts type line and its dictionary key (the key of its text and its card art).
nameThe shown name, from export_units.txt (empty if it has none).
category, classFor example infantry and spearmen.
kindThe category refined by weapon, as the toolkit's lists group units.
ownership, era0, era1, era2Lists of faction names.
soldier, officers, mount, ship, engine, animalThe battle model, the officers' models (a list), and what it rides, sails or pulls.
armour_models, attributesLists.
stat_pri, stat_sec, projectilesLists of the values on those lines, and the projectiles it fires.
mercenary, eoptrue for a mercenary unit; true for a unit in an M2TWEOP unit file.
fieldsEvery line of the block as text, by name: u.fields.stat_mental, u.fields["era 0"]. A repeated line is officer, officer#2, officer#3.
field_orderThe names in fields, in the order the block has them.
file, rawThe file it is in, and the whole block as the file has it.

toolkit.edit_unit(type, fields, options?)edit

Change a unit's lines. fields uses the names of unit.fields: a value is text, a number or a list; false removes the line. options can hold rename (a new type: every file that names the unit follows), dictionary (a new key), name, descr and descr_short (its shown name and descriptions in export_units.txt).

toolkit.edit_unit("Peasants", { stat_cost = { 1, 200, 100, 20, 30, 200, 4, 50 } },
                  { name = "Village Levy" })

toolkit.clone_unit(source, type, options?)edit

A new unit copied from one in the same mod, under a new type: its block, its text and its models (the Transfer screen's copy with a new name). options: dictionary (default: the type in lower case, every run of characters other than a-z, 0-9 and _ turned into one _, and _ trimmed from the ends: "Royal Peasants" becomes royal_peasants) and name (the shown name, default the type). A taken type or dictionary is refused.

toolkit.delete_unit(type, options?)edit

Delete a unit and, by default, the lines elsewhere that name it (recruitment, armies) and its export_units entry. options: keep_text = true keeps the text entry, remove_models = true also removes battle models only it uses, keep_refs = true leaves the other files alone.

Battle models (battle_models.modeldb)

toolkit.models() → Model[]read

Every entry, in file order.

toolkit.model(name) → Model or nilread

One entry by name, in any case.

A Model has name, scale, lods (each {mesh, distance}), textures and attachments (each {faction, texture, normal, sprite}), animations (each {mount, primary, secondary, primary_weapons, secondary_weapons}) and raw, the entry as text.

toolkit.edit_model(name, changes)edit

changes holds one of: raw (the whole entry as text), rename (a new name; units that use it follow), or texture paths set for every faction: texture, normal, sprite, attach_texture, attach_normal.

toolkit.edit_model("peasants", { texture = "unit_models/_units/my_peasants/textures/peasants.texture" })

toolkit.clone_model(source, name)edit

Add an entry copied from another, under a new name.

Mounts and factions

toolkit.mounts() → tableread

Each mount in descr_mount.txt and the battle model it uses: toolkit.mounts()["heavy horse"].

toolkit.factions() → {slot, name, culture}[]read

Every faction in descr_sm_factions.txt: its slot (the name files use, like england), its shown name and its culture.

Buildings (export_descr_buildings.txt)

toolkit.buildings() → Building[]read

Every building line, in file order.

toolkit.building(name) → Building or nilread

One building line, like "barracks".

A Building has name, convert_to, religion, levels (the level names in upgrade order) and blocks, one per level, each with name, settlement (city, castle, or empty for both), requires, scalars (cost, construction and the other single values, by name), upgrades, capabilities and faction_capabilities (each {keyword, args, requires, line}) and recruits (each {unit, initial, per_turn, maximum, experience, requires}).

toolkit.edit_building(line, level, changes)edit

Change one level. changes can hold settlement, requires, scalars (only the ones named change), upgrades (the whole list), and capabilities / faction_capabilities as a list of operations. An operation names an existing line by its line from a read; one without line is a new line; lines not listed stay as they are.

local b = assert(toolkit.building("barracks"), "this mod has no barracks line")
local lv = b.blocks[1]
assert(lv.capabilities[2], "this example needs two capability lines on the first level")
toolkit.edit_building(b.name, lv.name, {
  scalars = { cost = 500 },
  capabilities = {
    { line = lv.capabilities[1].line, delete = true },                      -- take one out
    { line = lv.capabilities[2].line, args = '"Peasants"  1  0.5  4  0' },  -- change one
    { keyword = "recruit_pool", args = '"Militia"  1  0.5  2  0',           -- add one
      requires = "factions { england, }" },
  },
})

An edit moves the line numbers after it, so read the building again before the next edit to it.

The recruitment sheet

toolkit.recruits() → Recruit[]read

Every recruit_pool line of the EDB, the rows of the toolkit's recruitment sheet. A Recruit has line, unit, building, level, settlement, section (capability or faction_capability), requires, and the four numbers initial, per_turn, maximum and experience.

toolkit.edit_recruit(line, changes)edit

Change a line's numbers: { maximum = 6, experience = 1 }. Numbers cannot go below 0 and experience is whole. Only the numbers are rewritten, so lines never move.

Mercenaries (descr_mercenaries.txt)

toolkit.mercenaries(campaign?) → MercPool[]read

Every pool of a campaign (default imperial_campaign). A MercPool has name, regions and units. Each unit line has place (from 1), name, exp, cost, replenish (two numbers), max, initial, crusading (true or false), and only when the line has them start_year, end_year, religions, events and factions (otherwise nil). A line the toolkit could not read has fault.

toolkit.edit_merc_unit(pool, place, edits, campaign?)edit

Change one unit line, named by its place: { cost = 300, replenish = { 0.1, 0.2 } }. false takes an option off (religions = false).

toolkit.add_merc_unit(pool, values, campaign?)edit

Add a line at the end of a pool: { name = "Swiss Pikemen", exp = 1, cost = 400, replenish = { 0.1, 0.2 }, max = 2, initial = 1 }.

toolkit.delete_merc_unit(pool, place, campaign?)edit

Take one line out. The lines after it move up one place.

Traits and ancillaries

toolkit.traits() → Trait[]read

Every trait in export_descr_character_traits.txt.

toolkit.trait(name) → Trait or nilread

A Trait has name, characters, hidden, exclude_cultures, no_going_back_level, anti_traits and levels; each level has name, threshold, description, effects_description, gain_message, lose_message, epithet and effects (each {attribute, amount}).

toolkit.edit_trait(name, changes)edit

Change the header (characters, hidden, exclude_cultures, no_going_back_level, anti_traits) or levels by their place. A level's effects, when given, replace all its effect lines. Levels are not added or taken out here.

toolkit.edit_trait("GoodCommander", { levels = {
  [2] = { threshold = 4, effects = { { attribute = "Command", amount = 2 } } },
} })

toolkit.ancillaries() → Ancillary[]read

Every ancillary in export_descr_ancillaries.txt.

toolkit.ancillary(name) → Ancillary or nilread

An Ancillary has name, type, transferable, image, unique, excluded_ancillaries, exclude_cultures, description, effects_description and effects.

toolkit.edit_ancillary(name, changes)edit

Change any of those fields but the name. effects, when given, replace all its effect lines.

Triggers

Triggers are the rules at the end of the traits and ancillaries files that give points or ancillaries. Each function takes the file as "traits" or "ancillaries".

toolkit.triggers(file) → Trigger[]read

A Trigger has name, when_to_test, conditions (each {term, args, joiner, negated}: joiner is and or or, empty on the first), effects (each {keyword, args}, like Affects GoodCommander 1 Chance 50) and raw, the block as text.

toolkit.edit_trigger(file, name, changes)edit

changes can hold name, when_to_test, conditions (all of them, in order) and effects (changes to the existing effect lines, in order). To add or take out an effect line, give raw: the whole block as text, which wins over the rest.

toolkit.edit_trigger("traits", "battle_won_commander", {
  conditions = { { term = "WonBattle" }, { term = "IsGeneral", joiner = "and" } },
})

toolkit.add_trigger(file, trigger)edit

Add a trigger at the end of the file:

toolkit.add_trigger("ancillaries", {
  name = "my_tutor_trigger", when_to_test = "CharacterComingOfAge",
  conditions = { { term = "IsGeneral" } },
  effects = { { keyword = "AcquireAncillary", args = { "tutor", "chance", 20 } } },
})

toolkit.delete_trigger(file, name)edit

Take one trigger out.

Text (.strings.bin)

The game reads its text from data\text\*.strings.bin archives. Each function takes the archive as "expanded", "expanded.txt" or "text/expanded.txt.strings.bin". Most archives tag each entry ({SOME_TAG}text); four (battle, shared, strat, tooltips) have no tags and are addressed by place from 1.

toolkit.strings(file) → {tag, value}[]read

Every entry, in file order. tag is empty in an archive with no tags.

toolkit.string(file, tag) → text or nilread

One entry's text, by tag or, in an archive with no tags, by place.

toolkit.edit_strings(file, changes)edit

Change many entries in one call: a tag that is there gets the new text, one that is not is added, false takes one out. An archive with no tags is keyed by place from 1 and only takes new text for entries it has: adding or taking out an entry there is refused, because the game finds those entries by their place and every one after it would move.

toolkit.edit_strings("expanded", { ENGLAND = "Kingdom of England", MY_NEW_TAG = "New text", OLD_TAG = false })

If the mod keeps a .txt beside the archive, the game may rebuild the archive from it; change the .txt too, or delete it, so the two agree.

The campaign map (descr_strat.txt)

These take an optional campaign folder name, imperial_campaign unless you say. Checks run against the mod's own map, so the mod needs data\world\maps\base.

toolkit.settlements(campaign?) → Settlement[]read

A Settlement has region, faction (the faction whose block it is in), kind (city or castle), level, population, year_founded, plan_set, faction_creator and buildings (each {line, level}). population and year_founded are nil when the file has no whole number there, so check before doing maths with them.

toolkit.edit_settlement(region, changes, campaign?)edit

changes can hold kind, level, population, year_founded, plan_set, faction_creator, buildings (the whole list, in order), owner (give it to another faction) with place ("first" makes it that faction's capital, or "last"), or raw, the whole block as text. Problems the settlement panel would show come back as warnings in the report.

toolkit.edit_settlement("London_Province", { population = 6000, level = "large_city" })
toolkit.edit_settlement("York_Province", { owner = "scotland", place = "last" })

toolkit.strat_objects(campaign?) → StratObject[]read

Every fort, watchtower and resource. A StratObject has kind, line, x, y, type, culture and, for a resource, name (timber, iron...).

toolkit.edit_strat_object(kind, x, y, changes, campaign?)edit

Find one by its kind and tile and change it: x and y move it, and type, culture, name, region change those; delete = true takes it out. A tile off the map is refused.

toolkit.add_strat_object(kind, values, campaign?)edit

Add one: toolkit.add_strat_object("resource", { x = 120, y = 88, name = "iron" }). A fort or watchtower is filed under the region its tile is in, unless you give region.

Faction clones

toolkit.clone_faction(source, new, options?)edit

The Factions screen's clone: a new faction copied from an existing one in every file it touches. options: label (its shown name) and art = false (copy no pictures). The game has a fixed number of faction slots; a mod that uses them all refuses a new one.

toolkit.mod and args

toolkit.mod.name is the mod's folder name and toolkit.mod.root its folder. args holds the values given as Arguments in the Lua tab or with --set; they are always text, so use tonumber(args.by) for a number.

What a script cannot do

Scripts run in a sandbox, so a script someone posts on a forum cannot harm your computer:

  • no io (no reading or writing files of its own), no os beyond os.time, os.clock and os.date, no debug, no load, loadfile or dofile, no compiled modules;
  • require reads only from the script's own folder;
  • every change goes through the toolkit's editors, into the one mod the run is for;
  • a run stops after 60 seconds or 256 MB.

It is still your mod: read a script you did not write before you apply it, and look at its dry run.

The Lua is version 5.4: string, table, math, utf8 and coroutine are there, with integers kept apart from decimals (3 // 2 is 1, 3 / 2 is 1.5).

Writing scripts in VS Code

The Lua tab completes the toolkit's names already. For longer scripts, Visual Studio Code with the Lua extension (by sumneko) completes and checks them too:

  1. Make a folder for your scripts.
  2. Run runtime\python.exe lua_cli.py annotations "C:\path\to\that\folder". It writes toolkit.lua (a description of every function, never run) and .luarc.json.
  3. Open the folder in VS Code. Typing toolkit. lists every function with its parameters, and a misspelt field is underlined.

Run the annotations command again after the toolkit updates, so new functions appear.

Questions

Will the game see my changes?

Yes: an applied run changes the mod's own files, the same files the game reads. Start a new campaign for changes to descr_strat.txt; most other changes apply when the game starts.

Can I undo an apply from last week?

Yes, from the Log, as long as the files have not been changed by something else since. If they have, the Log offers Revert to here on an older entry instead.

Does a dry run touch my files?

It writes them while it runs and puts every byte back at the end, then checks. That is how each edit can see the ones before it. Keep the game closed while you run scripts.

Why did my edit not change the shown name in game?

Shown names come from text files. edit_unit with options.name writes export_units.txt; if the mod ships a compiled .strings.bin of it the game may read that instead.

How do I find the right name for something?

Print it: for _, b in ipairs(toolkit.buildings()) do print(b.name) end. Every name in this guide's examples is from the base game; your mod's may differ.

Can a script write a new file, or read one?

No. A script works only through the functions in this guide. That is what makes it safe to run someone else's script.
